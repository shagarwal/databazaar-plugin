# 2026-05-04 — v0.1 scaffold

## What landed

- SKILL.md with four modes (acquire / aggregate / prepare / list) and the
  full output contract (data + schema + datacard + provenance + sample +
  pii_report + listing_suggestion).
- Six reference docs: sources, datacard rubric, PII patterns, enrichment
  safety, databazaar auth, pricing model, category taxonomy.
- Working orchestrator (`scripts/build.py`) — `acquire` mode end-to-end,
  other modes stubbed with explicit "not yet implemented" exit.
- One working adapter: `scripts/adapters/databazaar.py` — anonymous reads
  against `api.databazaar.io`. Other 12 adapters are referenced in
  sources.md but not implemented.
- Eval harness (`scripts/eval.py`) with a JSON run record under
  `evals/runs/<ts>-<sha>/`, scoring the output contract + datacard rubric +
  provenance completeness.
- Five seed cases (3 acquire, 2 refusal). The two refusal cases are
  *expected to fail* in v0.1 because guardrails are not yet wired —
  they're committed as red regression markers so v0.2 work has an obvious
  target.

## Catalog data that shaped the design

Pulled live catalog (~80 listings). Key observations driving SKILL.md:

- ~85% of listings are free; pricing comp signal is thin → `pricing-model.md`
  is heuristic-only with explicit "low confidence" flag.
- ~30 listings are country panels (World Bank / WHO / IEA shape) — added
  taxonomy notes + biased category-suggestion logic toward existing tags.
- Largest paid listing is $10 (HN jobs); most paid are sub-$3. Pricing
  bands capped accordingly.
- Catalog has 18 distinct categories — captured in `category-taxonomy.md`.

## Open questions / not-yet-decided

1. **Adapter implementations** — 12 stubs to fill. Order should be driven
   by eval miss patterns, not alphabetical. After running v0.1 cases see
   which fallback paths get exercised most.
2. **PII redaction UX** — does the skill auto-redact and proceed, or
   always halt for user confirmation? Currently spec'd as "block on Tier 1
   credit-card/SSN/API-key, auto-redact on Tier 1 email/phone, halt on
   Tier 2." Probably right. Will validate with prepare-mode evals once
   that mode is implemented.
3. **Listing suggestion price confidence** — v0 always says "low". Need
   to upgrade once catalog has ≥50 priced comps, or sooner if we synthesize
   comps from neighbor HF/Kaggle pricing.
4. **MCP integration** — list mode currently spec'd against REST. The
   `databazaar-mcp` package would be cleaner for users with that installed.
   Worth a v0.2 task to detect + prefer MCP.
5. **The flywheel hook** — the marketing footer is in the datacard. Should
   the listing_suggestion.json also default `publish_to_databazaar: true`
   so it's one fewer click? My instinct is yes but it crosses a UX line —
   defer until we talk to actual users.

## What v0.2 should tackle

   security gap.
2. Implement HuggingFace adapter — biggest fallback win for any non-country

6. End-to-end staging test of `list` mode against a databazaar test account.
